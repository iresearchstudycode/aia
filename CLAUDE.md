# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

VPAL (Voice-Powered AI Local) is a static web application — a secure, local-only AI chat interface with voice input/output, streaming responses, and 11 AI personas. It requires no build step; changes to files under `src/aia/` take effect immediately on reload.

## Running the Application

```bash
# Start the application
docker-compose up

# Access in browser
https://localhost/

# Reload Nginx config without restarting (for nginx.conf changes only)
docker exec vpal-nginx /usr/sbin/nginx -s reload

# Check container health
docker inspect --format='{{.State.Health.Status}}' vpal-nginx
```

**Prerequisites:**
- Docker Desktop running
- Ollama running on the Windows host at `localhost:11434` with both models pulled:
  - `ollama pull gemma4:e4b` — text + thinking model
  - `ollama pull gemma3:4b` — vision model (used automatically when an image is attached)
- `.env` file in the project root with `SECRET_KEY`, `USER_1`, `TOTP_SECRET_1` (see `auth/main.py` for all supported vars)
- Nothing extra for text-to-speech: the default **Piper** engine (`vpal-piper-tts`) is part of the compose stack and fully offline (the voice model is fetched + SHA256-verified during `docker-compose build`, so the first build needs network)
- (Optional) Voicebox running on the Windows host at its default port (`17493`) if you want the VoiceBox text-to-speech engine instead of Piper — the app works fully without it; selecting VoiceBox while it's unreachable just shows a toast error

## Branching & Release Workflow

Two long-lived branches: **`dev`** (integration) and **`master`** (released — the default branch; CI's `push`/`pull_request` triggers fire only here, and `auth-lint-test`, `frontend-lint`, and `nginx-config-check` are required status checks).

- **All PRs target `dev`** — feature work and Dependabot version updates alike (`.github/dependabot.yml` sets `target-branch: dev`). `master` then only ever moves through a release PR, so `dev` stays strictly ahead of it.
- **A release is one PR `dev` → `master`, merged with "Create a merge commit"** — never *Squash* or *Rebase*. Those rewrite the commits, orphaning `dev`'s history so that `dev` has to be `git reset --hard origin/master`'d after every release (this is what happened with [#17]). A merge commit leaves `dev`'s commits reachable from `master` and lets the next step be a fast-forward.
- **Right after merging, fast-forward `dev` up to `master`** so the two never drift:
  ```bash
  git checkout dev && git fetch origin && git merge --ff-only origin/master && git push origin dev
  ```
  This pulls in only the release merge commit — no force-push, because `dev` was already its ancestor. If `--ff-only` is rejected, a Dependabot *security* PR (which ignores `target-branch` and lands on `master` directly) got in; drop `--ff-only` to make an ordinary merge commit on `dev` and carry on.
- Bump the `VERSION` file (semver) and add the `- [x]` line(s) to `TODO.md` in the same PR that ships the change.

## Architecture

```
Browser → HTTPS (port 443) / HTTP (port 80 → redirects to HTTPS)
       → Nginx (Docker, cgr.dev/chainguard/nginx, uid=65532)
           ├── /auth/* → FastAPI auth service (cgr.dev/chainguard/python, uid=65532)
           │              POST /auth/login   — validates username + TOTP code, issues session cookie
           │              POST /auth/logout  — CSRF-verified, clears session
           │              GET  /auth/verify  — sub-request endpoint called by auth_request; 200 also returns X-Auth-User: <username>
           │              GET  /auth/setup   — one-time QR setup (requires SETUP_TOKEN env var)
           │              GET  /auth/me      — returns {"username":"..."} for the profile widget
           ├── auth_request /auth/verify (session gate applied to all routes below;
           │       auth_request_set captures X-Auth-User and forwards it to /settings)
           ├── GET/HEAD /* → serves static files from src/aia/
           ├── POST /ollama/api/chat (exact match) → reverse proxy → host.docker.internal:11434/api/chat
           ├── GET  /ollama/api/tags (exact match) → reverse proxy → host.docker.internal:11434/api/tags (lists installed models for the toolbar model selector)
           ├── piper-tts service (python:3.12-slim, uid=65532) — self-contained, voice model baked into the image
           │              POST /piper/speak          — text → raw audio/wav (offline neural TTS; default engine)
           ├── voicebox-proxy service (cgr.dev/chainguard/python, uid=65532) → host.docker.internal:17493 (local Voicebox app REST API)
           │              POST /voicebox/speak       — synthesize (or resolve from cache) + play; blocks until done
           │              GET  /voicebox/audio/{id}  — fetch a past generation's audio, for cache-hit replay
           ├── doc-extract service (cgr.dev/chainguard/python, uid=65532) — self-contained, no host dependency
           │              POST /doc-extract/extract  — PDF upload → extracted text (.txt/.md are read client-side, never reach this)
           ├── settings-service (cgr.dev/chainguard/python, uid=65532) — self-contained; SQLite/WAL on the vpal-settings-data volume
           │              GET  /settings                 — resolved {global, personas, defaults} for the X-Auth-User user
           │              PUT  /settings/global          — upsert a subset of global prefs
           │              PUT  /settings/persona/{key}    — upsert per-persona overrides (null value deletes)
           │              POST /settings/reset            — {scope: global|persona:<key>|all, keys?: [...]}
           └── conversations-service (cgr.dev/chainguard/python, uid=65532) — self-contained; SQLite/WAL on the vpal-conversations-data volume
                          GET    /conversations           — newest-first conversation metadata for the X-Auth-User user (?q= title filter)
                          GET    /conversations/search    — same shape, LIKE also matches message body text
                          GET    /conversations/{id}      — full record incl. body (history array)
                          PUT    /conversations/{id}      — client-generated id; upsert + per-user cap eviction + 1 MiB body cap
                          DELETE /conversations/{id}      — idempotent
```

Nginx handles TLS termination, HTTP→HTTPS redirect, and security headers (HSTS, CSP, X-Frame-Options). The container runs as a non-root user (uid=65532), read-only filesystem, with capabilities restricted to `NET_BIND_SERVICE` only.

## Docker Container Details

**Image:** `cgr.dev/chainguard/nginx` — distroless (no shell, no wget/curl). The healthcheck uses `nginx -t` (config validation) since no HTTP client is available. **Digest-pinned in `docker-compose.yml`** (`cgr.dev/chainguard/nginx:latest@sha256:…`) like the Python services' Dockerfiles — update with `docker pull cgr.dev/chainguard/nginx:latest` and copy the `Digest:` line.

**Writable paths (tmpfs):** `/var/lib/nginx/tmp` and `/var/run`, both owned by uid=65532. The container root filesystem is otherwise read-only.

**Capabilities:** Only `NET_BIND_SERVICE` is granted (to bind port 443 as non-root). All other capabilities are dropped.

**`host.docker.internal`** resolves to the Windows host via `extra_hosts: host-gateway`, allowing the Nginx proxy to reach Ollama at `localhost:11434`, and the `voicebox-proxy` service (which also sets `extra_hosts`) to reach the local Voicebox app at `localhost:17493`.

## Security Invariants

- All AI response content — both the final answer and thinking block content — passes through `renderMarkdownToHtml()` (`marked.parse()` → `DOMPurify.sanitize()`) before being set as `innerHTML` — in `api.js` (streaming and final rebuild) and `chat.js` (`renderConversationHistory`).
- User-supplied message text is inserted via `.textContent` (`addUserMessage`, `renderConversationHistory`'s user branch) — never parsed as HTML or Markdown, so it needs no separate escaping. `escapeHtml()` is used elsewhere for values interpolated into an HTML *template string* before it becomes `innerHTML` — timestamps and the error-message path in `api.js`.
- KaTeX (`renderMathIn()` in `chat.js`) always runs *after* `renderMarkdownToHtml()`, on the already-sanitized DOM — it never receives a raw HTML string, only already-inserted text nodes. `trust` is left at KaTeX's default of `false`, which disables `\href`, `\url`, `\includegraphics`, and the `\html*` macros — the only way a LaTeX source string could otherwise make KaTeX emit attacker-chosen HTML. Do not pass `trust: true` without re-reviewing this.
- highlight.js (`highlightCodeIn()` in `chat.js`) runs *after* `renderMarkdownToHtml()`, on the already-sanitized DOM. It emits only class-annotated `<span>`s (no attributes, no URLs), but its output is fed straight back through `DOMPurify.sanitize()` anyway — so the "every AI content → `innerHTML` boundary is sanitised" invariant holds with no special-casing for hljs. A block that throws is left as its plain (already-sanitised) text.
- Mermaid (`renderMermaidIn()` in `chat.js`) runs *after* `renderMarkdownToHtml()`. It is initialised once at load with `securityLevel: 'strict'` + `htmlLabels: false` (no click handlers, no external resource fetches, plain-SVG text labels) and its generated SVG string is passed through `DOMPurify.sanitize(svg, { USE_PROFILES: { svg: true, svgFilters: true } })` before it reaches `innerHTML`. A parse failure triggers one retry with `_repairMermaid()` (double-quotes unquoted punctuation in flowchart node labels — it only *adds* quotes, never markup, and its output goes through the same sanitiser); a diagram that still fails keeps its raw (already-sanitised) `<pre>` visible, marked `.mermaid-error` — it never blanks the message. `_colourCodeMermaidNodes()` then recolours nodes by shape via `.style.fill` DOM writes (no `innerHTML`). Do not lower `securityLevel` or re-enable `htmlLabels` without re-reviewing this (`htmlLabels: true` reintroduces `<foreignObject>`, which DOMPurify's SVG profile strips — the labels vanish).
- **Persona icon SVGs** (`personaIconEl()` in `chat.js`) arrive as strings from the settings-service (`GET /settings` `personas.<key>.icon`), so they go through the same `DOMPurify.sanitize(svg, { USE_PROFILES: { svg: true, svgFilters: true } })` boundary as Mermaid output before becoming a DOM node — even though the source is our own hardcoded `_PERSONA_ICONS` dict and the transport is same-origin. The `config.js` `personaIcons` fallback goes through the identical path.
- CSP: `script-src 'self'` has no `unsafe-inline`/`unsafe-eval` and is **unchanged** by the highlight.js / Mermaid / Piper / theming work — none of them needs an inline or `eval`/`Function` execution path in the browser (Mermaid's bundled lodash contains `Function("return this")` only as a global-object fallback that short-circuits on `self` before it is ever evaluated; the no-FOUC theme boot is a real file `theme-boot.js`, **not** an inline `<script>`, precisely because inline is blocked). All event handlers are wired via `addEventListener` in `main.js`. The vendored **Inter** `@font-face` `url()`s resolve same-origin (`/css/fonts/…`), covered by `default-src 'self'` since there is no `font-src` directive — no CSP change, and Google Fonts / any external font host would be blocked. `style-src 'self' 'unsafe-inline'` is the one deliberate exception — KaTeX positions glyphs via computed inline `style` attributes on the spans it generates (Mermaid also injects a `<style>` element, already covered by the same exception), with no CSS-class-only way to do that. `media-src 'self' blob:` is the other narrow allowance — `speakTextViaPiper()` fetches a WAV from `/piper/speak` and plays it via `URL.createObjectURL(blob)`; `blob:` in `media-src` only permits the page's own client-generated blobs (no external load, no exfil path), and without it `<audio src="blob:…">` falls through to `default-src 'self'`, which the browser rejects ("Media load rejected by URL safety check"). VoiceBox's cached-clip replay uses a same-origin `/voicebox/audio/{id}` URL, covered by the `'self'` part. The residual risk is bounded by the rest of the policy (`default-src 'self'`, `connect-src 'self'`, no external hosts in `img-src`), so an inline style still can't exfiltrate data or load an external resource. All other element visibility is controlled by CSS classes or `element.style.display` (unaffected either way — CSP only governs the `style` *attribute's contents*, not whether JS can set `element.style.display`).
- The streaming fetch in `api.js` is wired to a module-level `streamAbortController`; call `stopStreaming()` to cancel mid-stream. If tokens were received before abort, the partial response is saved to `conversationHistory`; the user message is only rolled back when nothing was generated.
- User input is capped at `MAX_INPUT_LENGTH` (4000) set programmatically on `#userInput` in `main.js`; Nginx enforces `client_max_body_size 1m` globally and `20m` on the `/ollama/api/chat` location to accommodate base64-encoded image payloads.
- `/voicebox/speak` is gated by the same `auth_request /auth/verify` session check as every other application route, and rate-limited (`voicebox_speak` zone, 10 req/min, burst 3) — Voicebox itself has no authentication of its own, so this endpoint is the only thing standing between an unauthenticated request and the host's speakers.
- `/piper/speak` is gated by the same `auth_request /auth/verify` session check and rate-limited (`piper_speak` zone, 10 req/min, burst 3). Piper is fully offline and self-contained — no host dependency, no `host.docker.internal` — so unlike VoiceBox it exposes nothing on the host; the input is validated server-side (non-empty, ≤ `PIPER_MAX_TEXT_CHARS`, ASCII control chars stripped) and the response is inert `audio/wav` bytes.
- `/ollama/api/tags` is `auth_request`-gated, rate-limited (`ollama_tags` zone, 12 req/min, burst 3), GET-only (`limit_except GET { deny all; }`), and exact-match — it's read-only, exposing model metadata only (never generation), and is the minimum surface the model selector needs. It plus `/ollama/api/chat` are the *only* Ollama paths reachable through the proxy; `/api/generate`, `/api/pull`, `/api/delete`, `/api/create`, `/api/copy`, `/api/push` stay denied.
- A document attachment's extracted text is folded into the same `content` string as the user's typed question (`buildDocumentMessageContent()`) and flows through the exact same `.textContent`-insertion path as any other user message — there is no separate code path, and therefore no separate injection surface, for document-derived text vs. typed text. `/doc-extract/extract` is gated the same way as every other route (`auth_request`) and rate-limited (`doc_extract` zone, 10 req/min, burst 3).
- The English Editor "changes" diff view (`renderEditorReply()` in `chat.js`) is assembled entirely with `document.createElement` / `document.createTextNode` / `.textContent` — never `innerHTML` or string concatenation — so it adds no new sanitisation-boundary surface (`<ins>` / `<del>` are in DOMPurify's default allowlist regardless). The "clean" view reuses `renderMarkdownToHtml()`, the same sanitised boundary every other reply goes through. The diff is always derived client-side from the verbatim stored model output — nothing diff-related is ever sent to or stored from the model.
- `/settings` and `/settings/` are `auth_request`-gated, rate-limited (`settings` zone, 30 req/min, burst 10), and GET/PUT/POST-only. The `settings-service` never sees the session cookie or `SECRET_KEY` — it trusts `X-Auth-User`, which nginx sets from the auth sub-request's response header (`auth_request_set` → `proxy_set_header`), **overwriting any client-supplied value**; the service additionally rejects a username not matching `^[A-Za-z0-9_-]{1,64}$`. It stores no secrets, and its settings values are validated against a strict per-key allowlist (enum/type) before hitting SQLite. The Settings lightbox (`settings.js`) opens no new AI-content → `innerHTML` boundary — its only `innerHTML` writes are two hardcoded SVG-icon string constants for the toolbar badges; all field values render via `.textContent` / form controls.

## Key Configuration

Build-time constants are in [src/aia/scripts/config.js](src/aia/scripts/config.js). **Since 1.23.0, every *user preference* (chat model, vision model, TTS engine, auto-speak, STT language, thinking mode + depth, navigator rail, per-persona overrides, editor mode, active persona) is served by the `settings-service` and resolved into the `current*` globals by `applyResolvedSettings()` — the `config.js` literals below are only the offline fallback, and the `localStorage` keys are read once by the migration then never again.** See [Consolidated Settings](#consolidated-settings) and [Settings Service](#settings-service); the house defaults are the `VPAL_DEFAULT_*` env vars.

- `MODEL_NAME` — offline-fallback text + thinking model (default: `gemma4:e4b`). The model actually sent is `currentModel`, resolved from `vpalSettings.global.chat_model` (Settings → Models), else this.
- `VISION_MODEL_NAME` — offline-fallback vision model (default: `gemma3:4b`). The model actually used is `currentVisionModel`, resolved from `vpalSettings.global.vision_model` (Settings → Models — **now user-selectable**), else this. `gemma4:e4b` has no vision encoder in its GGUF.
- `OLLAMA_API_URL` — proxied chat endpoint (default: `https://localhost/ollama/api/chat`)
- `OLLAMA_TAGS_URL` — proxied model-list endpoint (default: `https://localhost/ollama/api/tags`); GET-only, read by the Settings dialog to populate both model `<select>`s
- `SETTINGS_API_URL` — proxied settings endpoint (default: `https://localhost/settings`); `GET` on load, `PUT`/`POST` on Save/Reset
- `OLLAMA_MODEL_KEY` / `NAV_RAIL_KEY` / `EDITOR_MODE_KEY` / `PERSONA_PREFS_KEY` — legacy `localStorage` keys, read once by `_migrateLegacySettingsIfNeeded()` (`main.js`), never written
- `currentModel` — runtime global; the model sent on every text/thinking turn. Hydrated from the settings service; `MODEL_NAME` is the fallback.
- `currentNumCtx` / `modelContextLengths` — runtime globals (config.js). `modelContextLengths` is a `{ modelName: contextLength }` map parsed from `GET /api/tags` `details.context_length` (present on recent Ollama builds; absent for some models incl. the gemma line here) — populated once at load (`main.js`) and refreshed whenever the Settings dialog opens (`settings.js` `_settingsEnsureModelNames`). `currentNumCtx` is what `api.js` actually sends as `options.num_ctx`: `recomputeNumCtx()` (`settings.js`, called from `applyResolvedSettings()` and after each `/api/tags` fetch) sets it to `resolveNumCtx(currentModel, OLLAMA_NUM_CTX, modelContextLengths)` = **the model's full advertised context window when known** (qwen3:4b → 262144, deepseek-r1 → 131072), else the `OLLAMA_NUM_CTX` fallback (16384). This can send `num_ctx` far above `OLLAMA_NUM_CTX`; the **Ollama server's own `OLLAMA_CONTEXT_LENGTH` is the real cap**, so set that env var to the largest KV cache the host can afford. Unknown model (gemma line) → `OLLAMA_NUM_CTX` fallback, unchanged. `MAX_DOCUMENT_TEXT_CHARS` is sized against the 16384 fallback, so it stays safe even on a small-context model; a larger-window model just has more headroom.
- `currentVisionModel` — runtime global; the model used for image turns. Hydrated from the settings service; `VISION_MODEL_NAME` is the fallback.
- `OLLAMA_NUM_CTX` — the **fallback** `options.num_ctx` (default: `16384`), used only when the active model's context window is unknown. When it *is* known, `currentNumCtx` (above) is that full window instead — possibly much larger. Either way `num_ctx` is sent on every text/thinking request and every multi-turn-vision follow-up — never omitted, so behavior doesn't silently depend on Ollama's own default. The effective ceiling on what Ollama honours is the **server-side `OLLAMA_CONTEXT_LENGTH`**; size that to the host's KV-cache budget.
- `PIPER_SPEAK_URL` — proxied endpoint for the (default) Piper TTS engine (default: `https://localhost/piper/speak`)

- `currentThinkingMode` — runtime global (`'off' | 'low' | 'medium' | 'high'`); resolved by `resolveThinkingMode(activePersona, vpalSettings)` — the persona's `thinking_enabled`/`thinking_depth` override (Settings → Personas) falls through to the global `thinking_enabled`/`thinking_depth` (Settings → Reasoning), and `'off'` when disabled.

The default view for a new Consultant analysis artifact — see [Persona Affordance Templates](#persona-affordance-templates). `pendingConsultTemplate` (`'swot' | 'proscons' | 'matrix' | 'quiz' | 'flashcards' | null`) is the armed template consumed on the next send (Consultant composer pick or Teacher reply button).

## VoiceBox Proxy

The FastAPI VoiceBox proxy lives in `voicebox-proxy/`. It bridges the browser to a local Voicebox desktop app's plain REST API (typically at `127.0.0.1:17493` on the Windows host — Voicebox also exposes an MCP server, but the REST surface is simpler and is what exposes generation status and past-audio retrieval, which MCP alone doesn't) so AI responses can optionally be spoken through VoiceBox instead of the default Piper engine.

| File | Purpose |
|---|---|
| `voicebox-proxy/main.py` | FastAPI app. `_speak()`: on a cache hit, returns the cached generation id immediately; on a miss, `_start_generation()` (`POST /speak`) then `_await_completion()` (streams `GET /generate/{id}/status` until a terminal status) — Voicebox auto-plays the finished clip through the host's speakers as a side effect of this flow, with no way to opt out. `GET /voicebox/audio/{id}` proxies Voicebox's `GET /audio/{id}` so the browser can replay a cache hit itself (Voicebox does *not* auto-play for a lookup of a past generation) |
| `voicebox-proxy/Dockerfile` | Multi-stage Chainguard build (digest-pinned), mirrors `auth/Dockerfile` |
| `voicebox-proxy/requirements.txt` | Production dependencies (`fastapi`, `uvicorn`, `httpx`) |
| `voicebox-proxy/requirements-test.txt` | Test dependencies (`pytest`, `httpx`, `flake8`, `black`) |
| `voicebox-proxy/tests/test_main.py` | 31 pytest tests covering the generation cache, status-stream parsing, and route-level success/validation/failure cases |

**Generation cache** — `_generation_cache` is an in-memory `{sha256(profile + text) -> generation_id}` map, capped at 200 entries (oldest evicted first) and cleared on restart; same trade-off as the auth service's in-memory brute-force state, acceptable for a local single-user tool. A cache hit means *identical* text (and profile) only — no fuzzy matching.

Voicebox itself has no authentication of its own (any `X-Voicebox-Client-Id` header is accepted), so `VOICEBOX_CLIENT_ID` (default: `vpal`) is just an identifier, not a secret — the real access control is the Nginx `auth_request` gate in front of both `/voicebox/speak` and `/voicebox/audio/`.

Configurable via env vars (all optional, sensible defaults baked in): `VOICEBOX_URL` (base URL, no path suffix), `VOICEBOX_CLIENT_ID`, `VOICEBOX_TIMEOUT_SECONDS` (default `60` — must cover the slowest expected synthesis) — see `.env.example`.

## Math Rendering (KaTeX)

Purely client-side — no backend or Nginx routing involved beyond the existing static-file serving. `katex.min.js` + `katex-auto-render.min.js` are vendored (see [Updating Vendored Libraries](#updating-vendored-libraries)); `renderMathIn(element)` in `chat.js` wraps `renderMathInElement()` with the app's delimiter set and is called once per message at each terminal render point in `api.js`/`chat.js` (never on every live-streamed token — see the `api.js` row in [JavaScript Module Architecture](#javascript-module-architecture)).

**Delimiters supported:** `$$...$$` and `\[...\]` (display), `$...$` and `\(...\)` (inline), plus the AMS environments (`\begin{equation}`, `\begin{align}`, etc.). `$...$` is *not* one of `renderMathInElement`'s own defaults (it can clash with literal currency amounts) but is added explicitly since it's the form models emit most often — it's listed last in the delimiters array, which matters: `$` must come after `$$` or it would match `$$`'s first `$` instead.

**The markdown-mangling bug (and why `protectLatexDelimiters` exists):** `marked.parse()` always runs before KaTeX ever sees the text, and CommonMark's backslash-escape rule strips a backslash immediately before ASCII punctuation — silently turning `\(` into `(`, `\[` into `[`, `\{` into `{`, and `\\` into `\`. That destroys the `\(...\)`/`\[...\]` delimiters and matrix row separators before KaTeX gets a chance to match them (`\frac`, `\sqrt`, `\alpha` etc. are unaffected — backslash followed by a *letter* isn't in CommonMark's escape set). `protectLatexDelimiters()`/`restoreLatexBackslashes()` in `utils.js` swap the backslash for a `U+E000` placeholder before `marked.parse()` and swap it back afterward; `renderMarkdownToHtml()` in `chat.js` is the one function that does this consistently — **always route new AI/user content → `innerHTML` sites through it, never call `marked.parse()`/`DOMPurify.sanitize()` directly.** Regression tests: `tests/js/latex-protect.test.js`.

**Error handling:** a malformed expression (e.g. an unclosed brace) doesn't throw or blank out the message — `katex-auto-render.min.js` catches `ParseError` per-expression internally and falls back to rendering that one expression's raw source as plain text, leaving the rest of the message (and any other math in it) untouched.

**CSS:** `.message-content .katex-display` gets `overflow-x: auto` in `style.css` — KaTeX's own CSS sets `white-space: nowrap` on display-mode blocks, so a wide equation (long matrix, long sum) needs its own horizontal scrollbar rather than overflowing the chat bubble, mirroring how `.message-content pre` already handles wide code blocks.

## Code Highlighting (highlight.js)

Purely client-side, modelled on the KaTeX integration. `highlight.min.js` is vendored (highlight.js v11.11.1, the "common" ~40-language build; see [Updating Vendored Libraries](#updating-vendored-libraries)) and provides the `hljs` global. `highlightCodeIn(element)` in `chat.js` is folded into `enrichRenderedContent()` alongside `renderMathIn` and called once per message at each terminal render point in `api.js`/`chat.js` (never per live-streamed token).

**How it runs:** `marked.parse()` turns a ` ```js … ``` ` fence into `<pre><code class="language-js">…</code></pre>`. After that HTML is sanitised and inserted into the DOM, `highlightCodeIn()` walks each `pre code`, skips any `language-mermaid` block (Mermaid owns those) and any block already carrying `data-hljs-done`, then calls `hljs.highlightElement(block)`. `hljs.configure({ ignoreUnescapedHTML: true })` runs once at load to silence a benign console warning (we only ever feed it already-sanitised DOM).

**Security:** highlight.js emits only class-annotated `<span>`s, but its output is re-run through `DOMPurify.sanitize()` immediately (`block.innerHTML = DOMPurify.sanitize(block.innerHTML)`) so the "every `innerHTML` boundary goes through DOMPurify" invariant holds with no hljs carve-out. A block that throws is left as its plain (already-sanitised) text — `try { … } catch { /* leave as plain text */ }`.

**CSS:** `.message-content .hljs` overrides the vendored atom-one-dark theme's `#282c34` background to the app's existing `#1e293b` slate `<pre>` ground; token colours are left as the theme ships them.

## Diagrams (Mermaid)

Purely client-side, modelled on the KaTeX integration. `mermaid.min.js` is vendored (Mermaid **v10.9.3** UMD single-file bundle — ~2.8 MB, an accepted tradeoff for a local app; v11 restructured away from a clean UMD; see [Updating Vendored Libraries](#updating-vendored-libraries)) and provides the `mermaid` global, loaded last of the vendored scripts. `mermaid.initialize(...)` runs once at the bottom of `chat.js` with `securityLevel: 'strict'`, `htmlLabels: false`, `theme: 'base'`, and a **Rational Rose-style `themeVariables` block** (light "paper" canvas, cornsilk node fills, dark-navy borders, near-black text — see below). `renderMermaidIn(element)` in `chat.js` is folded into `enrichRenderedContent()`.

**`htmlLabels: false` is load-bearing, not cosmetic.** Mermaid v10 renders node labels inside `<foreignObject>` XHTML *even under `securityLevel: 'strict'`*, and DOMPurify's SVG profile strips `<foreignObject>` — so before v1.31.0 every diagram rendered with its **node text silently missing**. `htmlLabels: false` (set top-level *and* per diagram type — `flowchart` / `class` / `er`) forces plain SVG `<text>`/`<tspan>` labels, which survive the sanitiser.

**Rational Rose styling.** `theme: 'base'` + `themeVariables` gives every box the cornsilk (`#fff8dc`) fill, `#33334d` border and `#1a1a2e` text; the hex values mirror the `--mermaid-*` tokens in `style.css` (keep the two in sync — `chat.js`'s `ROSE` object points back). `_colourCodeMermaidNodes(wrapper)` then does a **DOM pass over the sanitised SVG** (plain `.style.fill` writes, no `innerHTML`, no new sanitiser surface) that recolours **flowchart nodes by shape**: a `polygon` child → decision → amber (`--mermaid-decision-bg`); a `circle`/`ellipse` or a stadium `rect` (`rx ≈ height/2`) → terminator → sage green (`--mermaid-terminator-bg`); everything else keeps the cornsilk. Other diagram types have no matching shapes and get the `themeVariables` treatment alone. The `.mermaid-diagram` wrapper itself gets the light paper background + a thin border in **both** app themes (the `--mermaid-*` tokens are defined once on bare `:root`, same call as `--code-bg` staying dark), so a diagram always reads like a printed model sheet.

**How it runs:** a ` ```mermaid … ``` ` fence survives `renderMarkdownToHtml()` as `<pre><code class="language-mermaid">…</code></pre>` (highlight.js skips it). `renderMermaidIn()` is `async` (Mermaid v10's `mermaid.render()` returns a Promise) and is called **fire-and-forget** — not awaited — at the render sites, so the diagram pops in a moment after the text, the same way KaTeX/highlight are non-blocking. For each `pre code.language-mermaid` it reads `code.textContent`, renders to an SVG string with a random id, wraps it in `<div class="mermaid-diagram">`, runs `_colourCodeMermaidNodes()`, and `replaceWith()`s the `<pre>`. A `data-mermaid-done` flag on the `<pre>` guards against a double render during the async gap.

**Auto-repair (`_repairMermaid`):** local models routinely emit `flowchart` / `graph` Mermaid that won't parse — unquoted `()` `[]` `{}` `#` `/` `:` `"` inside **node *and* edge** labels (`D{Web Application Firewall (WAF)}`, `-->|GET /api {"x":1}|`), a literal `\n` or `& \n` between node defs, `<br/>` tags, `classDef` / `:::class` colouring. When the raw source fails, `renderMermaidIn()` retries once with `_repairMermaid(src)` — it runs **only** as this second attempt so it can be aggressive (goal: "render something legible", not fidelity): it drops `classDef`/`style`/`linkStyle` lines and `:::class` tokens (nodes are colour-coded by shape instead), collapses the `\n` junk, strips `<br/>`, **balances `subgraph`/`end`** (models drop a closing `end` or tack a stray `subgraph X` onto the tail — it appends up to 20 missing `end`s; a balanced multi-word `subgraph Title` is left alone), and double-quotes node- and edge-label text that holds punctuation past `\w \s / . -`. `graph`/`flowchart` only; other diagram types returned as-is; pure, Node-exported, unit-tested. Only if the repaired source *also* fails does the block fall back to `.mermaid-error`. The `technical` persona's system prompt (`config.js`) also instructs `flowchart TD` + always-double-quoted labels + no `subgraph`/`style`/`classDef` to reduce how often the repair is needed.

**Orphan cleanup (`_cleanupMermaidOrphan`):** the vendored v10 `mermaid.render()` appends a throwaway measuring container (`#d<id>`) to `<body>` and does **not** remove it when the render throws. `renderMermaidIn()` cleans it up after each attempt — but only a node that is a **direct child of `<body>`**: the rendered SVG's own root element is `#<id>` (mermaid ids it after the render id), so a blind `getElementById(id).remove()` would delete the diagram itself.

**Security:** `securityLevel: 'strict'` disables click handlers and external resource fetches; `htmlLabels: false` keeps labels as plain SVG text. Both the raw and the repaired SVG output are passed through `DOMPurify.sanitize(svg, { USE_PROFILES: { svg: true, svgFilters: true } })` before reaching `innerHTML` (the repair only ever *adds* double quotes around existing label text; `_colourCodeMermaidNodes()` runs *after* sanitisation via `.style.fill` DOM writes, not `innerHTML` — neither adds markup). A diagram whose source fails to parse even after repair keeps its raw `<pre>` visible with a `.mermaid-error` class rather than blanking the message.

**CSP:** unchanged. `script-src 'self'` (no `unsafe-inline`/`unsafe-eval`) still holds — Mermaid v10.9 needs no inline/`eval`/`Function` execution path in the browser (the `Function("return this")` in its bundled lodash is a global-object fallback that short-circuits on `self` before evaluation). Mermaid's injected `<style>` element is covered by the `style-src 'unsafe-inline'` exception KaTeX already required. The `theme: 'base'` + `themeVariables` change is pure configuration data — no new code path. **If a future Mermaid bump reintroduces a `script-src`/`unsafe-eval` violation under this CSP, do not weaken the CSP** — pin back, or move to an SVG-only server-side render.

**CSS:** `.mermaid-diagram` gets the light paper canvas + thin border + `overflow-x: auto`. Flowcharts render at **natural size** (`flowchart.useMaxWidth: false`) and scroll horizontally inside that container when wide — legible beats shrink-to-fit, which had squashed a wide flowchart's label text down to a few pixels; `.mermaid-diagram svg` is `display: block; margin: 0 auto` so a narrow diagram centres and a wide one scrolls from its left edge. Other diagram types keep mermaid's own fit-to-width inline style. A `!important` safety-net rule forces `.mermaid-diagram text` / `.nodeLabel` / `tspan` to `--mermaid-text` so the label text is legible on the cornsilk boxes regardless of what mermaid's own computed `<style>` sets.

## Conversation Navigator Rail

Purely client-side (`src/aia/scripts/nav-rail.js`; see the [JavaScript Module Architecture](#javascript-module-architecture) row). A thin vertical strip of markers on the right inner edge of `.chat-messages` — one per **completed user turn** — for jumping around a long conversation. `.nav-rail` is `position: absolute` and now anchors to `#appMain` (`position: relative`); `nav-rail.js` is unchanged by the v1.26.0 shell move (it targets `#navRail` / `#chatMessages` by id).

**Behaviour:** markers are evenly spaced and the group is vertically centred (`justify-content: center`, `gap: 0`, each marker a 28×14 px transparent hit box with a 2 px `::before` tick). Hovering the rail widens every tick and shows a floating dark preview card (`.nav-rail__card`): a single-line ellipsised question title + a ≤25-word snippet of that turn's AI reply, with a caret pointing at the marker. Clicking a marker scrolls that user turn to the top of the viewport (`scrollIntoView({ behavior: 'smooth', block: 'start' })`) and flashes the message bubble for 1 s (`.nav-rail-flash`). One highlight state only: an `IntersectionObserver` rooted at `#chatMessages` keeps `.nav-rail__marker--active` on the turn nearest the viewport top; a click just scrolls there and the observer reassigns. **Mouse-only** — markers are not focusable and there are no keyboard shortcuts.

**Derivation & timing:** the rail is rebuilt from the DOM (`.message.user-message` + the following `.message.ai-message`) by a ~150 ms-debounced `MutationObserver`, so it settles once a turn completes and never updates mid-stream. `nav-rail.js` reads nothing from other modules' internals, and **nothing rail-related is written to saved-chat JSON** — it is purely a view over the live transcript.

**Toggle:** the navigator rail is now toggled from **Settings → Interface** (`nav_rail`); `applyResolvedSettings()` calls `setNavRailEnabled()` on hydration and after every Save. `NAV_RAIL_KEY` / `currentNavRailEnabled` / the `window.currentNavRailEnabled` mirror all remain (the migration reads the legacy key once; `nav-rail.js` still reads the flag off `window`).

**CSS:** all selectors are scoped under `.nav-rail` / `#navRail` / `#navRailToggle` / `.nav-rail-flash`. The one out-of-namespace addition is a thin custom scrollbar on `.chat-messages` (`scrollbar-gutter: stable` + an 8 px `::-webkit-scrollbar` + `scrollbar-width: thin`) so the rail clears it — additive only. `@media (max-width: 600px)` hides the rail **and** its toggle button. The flash animation lives under `@media (prefers-reduced-motion: no-preference)` with a static-outline fallback under `prefers-reduced-motion: reduce`. **CSP:** unchanged — no inline/`eval` path; the one `nav-rail.js` inline-style write is `card.style.top` (an offset number), already covered by the `style-src 'unsafe-inline'` exception KaTeX required.

**`aria-hidden="true"` on `#navRail`** is deliberate for this version — the rail is a supplementary, mouse-only aid and every turn it points at is reachable by scrolling; revisit if it ever becomes keyboard-operable.

## Theming

Since **v1.28.0** the whole UI is a ChatGPT-style near-monochrome design with **System / Light / Dark** themes. Purely client-side + the one settings key.

**Token model (`src/aia/css/style.css`).** Every colour in the file resolves from a `var(--…)` token — there are **no raw hex/`rgba()` outside the `:root` / theme blocks** (enforced by `grep`; v1.27.2 tokenised the lot with no visual change, this version rebased the values). Base hues are `r, g, b` triples (`--color-accent-rgb` etc.) so tinted `rgba()` values track one source. Three blocks define the values:
- bare **`:root`** — the complete **light** palette (`color-scheme: light`).
- **`@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { … } }`** — dark overrides for the "system" default (no `data-theme` attribute). The `:not([data-theme="light"])` guard means an explicit Light choice always gets bare `:root`.
- **`:root[data-theme="dark"] { … }`** — the same dark overrides again, for an explicit Dark choice under a light OS. **Keep the two dark lists identical.**

**`data-theme` contract.** `theme-boot.js` (first script in `<head>`, before `style.css`) stamps `data-theme="light"｜"dark"` from `localStorage['vpalTheme']` before first paint. `'system'` / absent → no attribute. `settings.js` `_applyTheme(mode)` (called from `applyResolvedSettings()`) keeps it in sync at runtime: sets/clears the attribute, mirrors to `localStorage[THEME_KEY]`, and wraps the swap in an `<html>.theme-switching` class (`* { transition: none !important }`) + a forced reflow (`void root.offsetWidth`) — without that, some Chromium builds don't re-evaluate a `transition`ed `background: var(--token)` when the token changes via the attribute toggle (verified: the send button stayed the wrong colour). `<meta name="color-scheme" content="light dark">` + the `color-scheme` CSS prop make native controls/scrollbars follow.

**`theme` setting.** A plain global key in the settings-service (`system｜light｜dark`, `_THEMES` enum, `VPAL_DEFAULT_THEME` default `system`), edited in **Settings → Interface**, resolved by `resolveSetting('theme', …)` like any other global. No migration mapping (new key, no legacy `localStorage`).

**Font.** Inter, vendored as `src/aia/css/fonts/inter-latin-wght-{normal,italic}.woff2` (variable, latin subset, ~100 KB total; via `npm pack @fontsource-variable/inter`). Two `@font-face` rules at the top of `style.css`; `body` stack is `'Inter', ui-sans-serif, -apple-system, …` (Inter first, ChatGPT's own fallback chain behind). Not SRI-pinned (SRI covers only the top-level tag); `*.woff2 binary` in `.gitattributes`. Same-origin `url()` → covered by `default-src 'self'` (no `font-src`), no CSP change. Code blocks use a system `ui-monospace` stack.

**Code blocks stay dark in both themes** (`--code-bg: #0d0d0d`) — matches ChatGPT and keeps the vendored `atom-one-dark` highlight.js theme correct.

**Login page** (`auth/static/login.css`, served by `auth/`) got the same monochrome treatment with a `@media (prefers-color-scheme: dark)` block — **system-preference only**, **system font only** (it loads before the app, reads no app storage, and the Inter woff2 isn't shipped into the auth image).

Each category panel has its own **Save + Cancel + Reset this section**; the footer has **Reset all**; a per-field ↺ appears only when a value differs from its default. Switching category with unsaved edits shows an inline discard confirm; Escape / backdrop / ✕ behave like Cancel-all; a local focus trap keeps Tab inside the dialog. On narrow widths the panes stack. The **Personas** category has an *active persona* `<select>` (redundant with the header picker, disabled while `conversationHistory.length > 0`) plus, per persona, override selects for thinking mode / depth / TTS engine (each with an "Inherit" = `null` option) and — for `englishEditor` only — the editor output mode; each persona's icon + name head the override panel and its system prompt is shown read-only in a disclosure. **Everyday persona switching is the header `#personaMenu`** (now `icon | name | ✓` rows); **this category is the detail view.**

**State flow** — `main.js` (`DOMContentLoaded`, now `async`) `GET`s `SETTINGS_API_URL` into `window.vpalSettings` (`{global, personas, defaults}`), runs the one-time migration, then `applyResolvedSettings()` pushes resolved values into the `current*` globals + badges + `updateSystemPromptState()`. Save → `diffSettings()` → `PUT /settings/global` or `/settings/persona/{key}` → the response is merged back into `window.vpalSettings` → `applyResolvedSettings()` → toast. **No reload, ever.** Resolution precedence: `env default → per-user global → per-user persona override` (`resolveSetting` / `resolveThinkingMode` / `resolveTtsEngine`).

**Migration** — on first load after upgrade (`localStorage['settingsMigrated'] !== '1'`), `_migrateLegacySettingsIfNeeded()` builds a payload from `buildMigrationPayload({ollamaModel, ttsEngine, autoTTS, thinkingOn, thinkingDepth, navRailEnabled, editorMode, personaPrefs})`, `PUT`s it, removes those keys, and sets the flag. After this, `localStorage` holds no preference state. `readPersonaPref` / `writePersonaPref` / `normalizeTtsEngine` / `migrateEditorModeValue` in `utils.js` are no longer called by app code (kept with their unit tests — cleanup candidate).

**Resilience** — if the `GET` fails, `window.vpalSettings` is built from the `config.js` constants with `__unavailable: true`, a toast fires, and the app is fully usable for chat; the lightbox renders a "can't reach the service / Retry" state (`window.__vpalRetrySettings`) with Save disabled.

**Backup (`#settingsBackup` in the footer)** — **Export settings** downloads the raw `GET /settings` payload as `vpal-settings-<YYYYMMDD-HHMMSS>.json`. **Import settings** (`#settingsImportInput`, hidden `<input type=file>`) parses a JSON file, validates it looks like an export (`.global` object present — else toast "Not a settings file"), then `PUT`s `parsed.global` to `/settings/global` and each persona's non-null overrides to `/settings/persona/<k>`, re-`GET`s, and re-applies. All ids are `settings*`-scoped to stay clear of the history lightbox's `history-*` CSS; they reuse the `.settings-section-reset` button style.

**Security** — the lightbox adds no new `innerHTML` sink for model output; the only `innerHTML` writes are hardcoded SVG-icon constants for the badges. `settings.js` reads/writes only same-origin `/settings`. See [Settings Service](#settings-service) for the backend and the `X-Auth-User` trust boundary.

**Adding a setting** — (1) add the key + validator to `settings-service/main.py`'s allowlist and its env default; (2) add a `VPAL_DEFAULT_*` line to `.env.example`; (3) render a field for it in the right category in `settings.js` and resolve it in `applyResolvedSettings()`; (4) add a migration mapping in `buildMigrationPayload` if a legacy `localStorage` key existed.

## Settings Service

The FastAPI settings service lives in `settings-service/`. It persists per-user preferences in **SQLite** (Python stdlib `sqlite3`, WAL) so they follow the user across devices and survive restarts.

| File | Purpose |
|---|---|
| `settings-service/main.py` | FastAPI app. `GET /settings` → resolved `{global, personas, defaults}`; each `personas.<key>` carries a read-only **`icon`** (an inline SVG from `_PERSONA_ICONS`, set in `_resolved_persona` after the stored-value merge so it can never be PUT or reset — matched offline by `config.js` `personaIcons`). `PUT /settings/global` / `PUT /settings/persona/{personaKey}` (partial bodies; a `null` persona value deletes that override row); `POST /settings/reset` (`{scope: "global"｜"persona:<key>"｜"all", keys?: [...]}`). An `active_persona` stored for a since-removed persona is coerced to the house default in `_resolved_global`. `GET /health` (unauthenticated, not proxied publicly). Identity comes from the `X-Auth-User` header (see below); a missing/malformed value (`^[A-Za-z0-9_-]{1,64}$`) → 401. Strict per-key allowlist with type/enum validation → 422; unknown persona → 404. Fresh `sqlite3.connect(timeout=5)` per request; table + `/data` created in the `_lifespan` startup hook. |
| `settings-service/Dockerfile` | Multi-stage Chainguard build (digest-pinned, same pins as `auth`/`doc-extract`), non-root uid 65532, port 8005. The builder seeds `/app/data_seed/.keep`; the runtime `COPY --from=builder --chown=65532:65532 /app/data_seed/ /data/` materialises `/data` owned by uid 65532 — Docker then initialises the empty `vpal-settings-data` named volume from that directory's contents **and permissions** on first mount, so the non-root process can write `settings.db` + the `-wal`/`-shm` sidecars. (The Chainguard build stage runs as nonroot and can't `mkdir` at `/`, hence the seed-dir dance.) |
| `settings-service/tests/test_main.py` | ~69 pytest tests — `conftest.py` points `SETTINGS_DB_PATH` at a per-test tmp file, so they hit real SQLite with no volume. Covers CRUD, per-user scope isolation, reset (per-field / per-scope / all), env-default fallback, every validation rejection, missing/malformed `X-Auth-User`, persona-key validation, `theme` enum, the read-only per-persona `icon`, and the removed-persona `active_persona` fallback. |

**The `X-Auth-User` trust boundary** — `settings-service` has no session logic of its own. `auth/main.py`'s `/auth/verify` returns `X-Auth-User: <username>` on a valid session (recovered from the signed `vpal_session` cookie via the shared `_session_username` helper). Nginx captures it with `auth_request_set $auth_user $upstream_http_x_auth_user` and forwards it as `proxy_set_header X-Auth-User $auth_user` — which **overwrites any client-supplied `X-Auth-User`**, so the service can trust the header. The `^[A-Za-z0-9_-]{1,64}$` check in the service is defence-in-depth behind the nginx `auth_request` gate. `SECRET_KEY` is **not** shared with `settings-service`.

**Config** — env vars, all optional (fallbacks baked in; documented in `.env.example`): `SETTINGS_DB_PATH` (default `/data/settings.db`) and the 9 house-default keys `VPAL_DEFAULT_CHAT_MODEL` (`gemma4:e4b`), `VPAL_DEFAULT_VISION_MODEL` (`gemma3:4b`), `VPAL_DEFAULT_TTS_ENGINE` (`piper`), `VPAL_DEFAULT_AUTO_SPEAK` (`false`), `VPAL_DEFAULT_STT_LANG` (`en-US`), `VPAL_DEFAULT_THINKING` (`false`), `VPAL_DEFAULT_THINKING_DEPTH` (`medium`), `VPAL_DEFAULT_NAV_RAIL` (`true`), `VPAL_DEFAULT_THEME` (`system` — `system｜light｜dark`). `active_persona` always defaults to `englishEditor` (not env-configurable). Update the Chainguard digest pins the same way as the other services (see **Updating Chainguard base image digests**).

## Conversation History

An auto-saved, searchable list of past conversations, persisted **per authenticated user** by a `conversations-service` (FastAPI + stdlib SQLite/WAL on the `vpal-conversations-data` named volume), reached through nginx at `https://localhost/conversations`. It is a convenience layer **on top of** the unchanged manual JSON Save / Export MD / Open (now in the main-pane `⋯` overflow menu).

- **Frontend** — `src/aia/scripts/history.js` (loaded after `settings.js`, before `main.js`), `CONVERSATIONS_API_URL` in `config.js`. See the `history.js` row in [JavaScript Module Architecture](#javascript-module-architecture). Since v1.26.0 the list renders **inline in the left app sidebar** (`#appSidebar` → `#historyList`), not a modal — the shell markup is static in `index.html` and `initHistory()` only binds handlers + fetches. Cards mark the active conversation (`.history-card.is-active`, via `resolveActiveCardId`) and the list re-renders out-of-band via `hcRefreshSidebar()` (debounced ~800ms) after each completed turn / load / delete / New chat, so a new conversation appears and its title updates without a reload.
- **Auto-save on every turn** — `api.js` fires `hcTouchCurrent()` (fire-and-forget) at each of its three turn-complete points; on a successful PUT it calls `hcRefreshSidebar()`. The client mints the conversation id (`'c-' + timestamp + '-' + random`, validated `^[A-Za-z0-9_-]{1,64}$` server-side) so it can `PUT` from the first turn. `conversationRecordFrom()` sends `{title, persona_key, message_count, body}` only — **not** `id` (it travels in the PUT URL; the service 422s an unknown body key). `main.js`'s `beforeunload` calls `hcBeaconSave()` (`keepalive` fetch) for a best-effort final save.
- **"New chat"** — the sidebar's `#newChatBtn`, `Ctrl/Cmd+Shift+O`, or `hcNewChat()`. `clearChat()` is `async` and `await`s `hcArchiveCurrent()` — a `PUT` of the still-populated `conversationHistory` — *before* wiping, so nothing is lost and there is no destructive `confirm()`; it then mints a fresh id and calls `hcRefreshSidebar()`.
- **Grouped by persona** — the list renders as collapsible groups, one per persona (`groupConversationsByPersona()`), most-recently-used persona first, a trailing **Unassigned** group for threads with no `persona_key`. A since-removed persona (`claudePromptCompressor`) keeps its own labelled group via `HISTORY_REMOVED_LABELS`. Collapsed groups persist in `localStorage[HISTORY_GROUPS_KEY]` (client-only, malformed-safe, never synced — the `SIDEBAR_STATE_KEY` pattern). The group holding the active conversation is always expanded and scrolled into view. Group headings carry the persona icon (`personaIconEl`); the old per-card persona chip is gone.
- **Loading a chat restores its persona** — `hcLoadConversation()` `await`s `setActivePersona(data.persona_key)` before rendering, so follow-up turns continue under the persona the conversation was created with. A new chat keeps whatever persona is currently active. A conversation with no / an unknown stored `persona_key` leaves the active persona untouched (and `setActivePersona` no-ops an unknown key; `settings-service` coerces an unknown stored `active_persona` back to the default on `GET`).
- **`X-Auth-User` reuse** — identical trust boundary to `settings-service`: nginx forwards `X-Auth-User` from `/auth/verify`, overwriting any client value; the service scopes every row to that username and 404s (never 403) a cross-user id. No auth change, no `SECRET_KEY` sharing.
- **Local-service-down degradation** — chat never blocks on `/conversations`. Auto-save failures are silent and retried on the next turn; user-initiated actions (load / delete / search) show a toast on failure.
- **Cap** — `CONVERSATIONS_MAX_PER_USER` (default 100): a `PUT` that would exceed the cap evicts the oldest by `updated_at` rather than failing.

## Persona Affordance Templates

Per-persona affordances that make a reply render as a structured, interactive artifact. Built on the English Editor pattern (`editor_mode` + `renderEditorReply` + a per-message view `<select>` + a tag round-tripped through save/load). Two personas so far:

| persona | templates | trigger | render |
|---|---|---|---|
| **Professional Consultant** | `swot`, `proscons`, `matrix` | composer **"Templates"** menu (`#consultTemplateBtn`) | colour-coded grid / interactive weighted table |
| **Patient Teacher** | `quiz`, `flashcards` | **"Quiz me" / "Flashcards"** buttons on a completed Teacher reply | clickable MCQ with reveal + explanation / flip cards |

**`_CONSULT_TEMPLATES` (`config.js`)** — `{ label, persona, format, … }` per key. Consultant's carry a `scaffold` (composer prefill); Teacher's carry a `prompt` (the whole follow-up message). The generic name (`consult*`) predates Teacher — the mechanism is now persona-agnostic; each template is gated to its `persona`.

- **Trigger → send.**
  - Consultant: `_syncConsultUiForPersona()` (`main.js`, from `updateSystemPromptState()`) shows `#consultTemplateBtn` only for `professional` (toggles `[hidden]` **and** inline `style.display` — `.voice-btn { display: flex }` beats `[hidden]`). The menu is built from templates that have a `scaffold`. Picking one prefills `#userInput`, arms `pendingConsultTemplate`, shows `#consultTemplateChip`; `_resolveOutgoing()` (shared by both send paths) folds `format` in via `_composeConsultMessage()` and passes the key down `_dispatchSend` → `streamOllamaResponse(..., consultTemplate)`.
  - Teacher: `_appendLearnActions(actionsDiv)` (`chat.js`) adds the two buttons to any plain Teacher reply's `.message-actions` (in `api.js` at turn-complete and in `renderConversationHistory`, gated by `_teacherLearnEligible(msg)` = `persona === 'teacher' && !msg.consultArtifact && has content`). A button calls `_requestLearnArtifact(kind)` → `_dispatchSend(prompt + '\n\n' + format, null, null, kind)`.
- **Tagging + render.** In `api.js`, a `consultTurn` (`_CONSULT_TEMPLATES[consultTemplate]` exists, active persona === its `.persona`, `!isVision && !thinkingActive && !isEditorExchange`) whose reply parses (`parseConsultReply(text, template)` → `parseSwotSections` / `parseProsConsSections` / `parseDecisionMatrix` / `parseQuiz` / `parseFlashcards`, all tolerant, `null` on failure — `parseDecisionMatrix`/`parseFlashcards` share `_splitMarkdownTable`) is tagged `assistantEntry.consultArtifact` + `.consultView` (`currentConsultView` for Consultant, always `'structured'` for Teacher) and rendered by `renderConsultReply(container, rawText, template, view, entry)` (`chat.js`):
  - `swot` / `proscons` → `.consult-grid` of `.consult-cell--{…}`, bodies via `renderMarkdownToHtml()`.
  - `matrix` → `_renderDecisionMatrix()` — `<table class="consult-matrix">` with a **0–5 weight slider per criterion** that live-recomputes `Σ score×weight` totals + winning row; weights are the one persisted user state (`entry.consultWeights`). api.js re-renders it once after `assistantEntry` exists so sliders bind to the real entry.
  - `quiz` → `_renderQuiz()` — `.consult-quiz` of question cards; clicking an option (or "Show answer") reveals the correct choice (green) + the explanation for that question; state is **per-render, not persisted** (a quiz is meant to be retaken).
  - `flashcards` → `_renderFlashcards()` — `.consult-flashcards` grid of `<button>` cards that CSS-flip (`is-flipped`, `prefers-reduced-motion` → no rotate); flip state per-render.
  - `text` → a plain reply. `_buildConsultViewSwitch()` gives a per-message Structured/Text `<select>` (reuses `.editor-view-switch`), passing `entry` through. A parse failure falls back to the plain render, untagged.
- **Round-trip.** `consultArtifact` / `consultView` / `consultWeights` are carried through the same 3 mappers as `editorExchange`/`editorView` — `saveChat` / `handleOpenFile` (`chat.js`, weights sanitised to ints 0–5) / `conversationRecordFrom` (`history.js`) — and `renderConversationHistory` has a `consultArtifact` branch (passes `msg`) before the editor branch.
- **Setting.** `default_analysis_view` (`structured｜text`) — professional-only, special-cased in `settings-service` `_validate_persona` / `_resolved_persona` / `_persona_defaults` like `editor_mode`, rendered in `settings.js` `_settingsRenderPersonaOverrideFields` (via a `def.fallback` field), resolved in `applyResolvedSettings()` → `currentConsultView`. Teacher artifacts have no setting.

**SECURITY:** every structured renderer is `createElement`-built; markdown-bearing parts (SWOT/pros-cons cell bodies, quiz question/explanation, flashcard back) go through `renderMarkdownToHtml()` (the one sanitised AI-content → `innerHTML` boundary); everything else (matrix option/criterion names, quiz option text, flashcard front) is `.textContent` — no new sink. `--consult-*` colour tokens are on bare `:root` + both dark blocks (theme-aware); quiz/flashcard rules reuse existing `--color-success*` / `--color-danger*` / `--consult-*` tokens.

## Document Text Extraction (doc-extract)

Lets a user attach a `.txt`, `.md`, or `.pdf` file and ask questions about it. `.txt`/`.md`/`.markdown` are read entirely client-side (`file.text()`) and never reach a backend — only `.pdf` needs a real parser, handled by a new `doc-extract/` FastAPI service (`pypdf`).

| File | Purpose |
|---|---|
| `doc-extract/main.py` | FastAPI app. `_extract_text()` reads every page via `pypdf.PdfReader`, joins non-blank pages with a blank line, and raises `ExtractionError` for encrypted or unparseable PDFs; the route layer additionally validates content-type/extension, upload size, and applies a generous server-side sanity cap on returned text length |
| `doc-extract/Dockerfile` | Multi-stage Chainguard build (digest-pinned), mirrors `auth/Dockerfile` |
| `doc-extract/requirements.txt` | Production dependencies (`fastapi`, `uvicorn`, `python-multipart`, `pypdf`) |
| `doc-extract/requirements-test.txt` | Test dependencies (`pytest`, `httpx`, `flake8`, `black`) |
| `doc-extract/tests/test_main.py` | 16 pytest tests covering text-joining/blank-page/encrypted/malformed-PDF cases (mostly `pypdf.PdfReader` mocked) plus two full end-to-end tests against the real `pypdf` with genuinely invalid bytes |

Unlike `auth`/`voicebox-proxy`, `doc-extract` needs no `extra_hosts`/`host.docker.internal` — it's entirely self-contained, with no external app or host service to reach.

**Why there's no separate "documents" field:** Ollama's chat API has a first-class `images` array for vision, but nothing equivalent for arbitrary text attachments. The extracted text has to be folded directly into the message's own `content` string. `buildDocumentMessageContent(name, text, truncated, question)` (`utils.js`) wraps it in a delimited block followed by the question (or a default prompt if none was typed):

```
--- Attached file: notes.pdf ---
<extracted text>
--- End of notes.pdf ---

<question>
```

This is what's actually sent to Ollama *and* what's stored in `conversationHistory` — meaning it's automatically resent on every subsequent turn along with the rest of the history, which is what makes follow-up questions about an already-attached document work with no special-casing.

**Display vs. storage — `parseDocumentMessageContent()`:** showing that full block in the chat bubble would be a poor experience for a 28,000-character document, so `addUserMessage()`/`renderConversationHistory()` call `parseDocumentMessageContent()` (the inverse of `buildDocumentMessageContent()`, matched via a regex with a backreference so the header/footer filename must agree) on the *same* stored `content` to recover `{ documentName, question }` for display — a filename chip (`_appendDocumentChip()`) plus just the question. Nothing is duplicated or stored differently; the split is purely a display-time parse of the one canonical string.

**Truncation:** extracted text is capped at `MAX_DOCUMENT_TEXT_CHARS` (28,000 — `truncateDocumentText()` in `utils.js`, applied uniformly to all three file types in `main.js`) before being folded into the message, independent of doc-extract's own much larger 200,000-char server-side sanity cap (`_MAX_TEXT_CHARS` in `doc-extract/main.py`) — the frontend constant is the one that actually governs context-budget behavior; the backend one just bounds worst-case response size for a pathological PDF. The whole conversation history (including this text) is resent to Ollama on every turn, so an unbounded document would make every subsequent message more expensive, not just this one. 28,000 chars is ≈7K tokens at ~4 chars/token, sized against the 16384 `OLLAMA_NUM_CTX` **fallback** (see [Key Configuration](#key-configuration)) so it stays safe on a small-context model — leaving roughly half that context for the system prompt, history, thinking budget, and the response. A model with a larger advertised window (`currentNumCtx`) simply has more headroom; raising `MAX_DOCUMENT_TEXT_CHARS` past ~7K tokens would still risk overflow on a 16K-fallback model, so keep it conservative.

**Validation:** extension-based on the frontend (`.txt`/`.md`/`.markdown`/`.pdf`) and both content-type *and* filename-extension based on `doc-extract` (some browsers send `application/octet-stream` for a `.pdf`). Encrypted and scanned/image-only PDFs are rejected — pypdf can open the former but VPAL treats it as a hard error rather than prompting for a password; the latter parses successfully but yields no extractable text, which `main.js` detects and reports as an error rather than silently attaching an empty document.

## Piper TTS

The FastAPI Piper TTS service lives in `piper-tts/`. It synthesises speech from text entirely offline with a local [Piper](https://github.com/OHF-Voice/piper1-gpl) neural voice (ONNX model + bundled espeak-ng phonemisation) and is the **default** speech-synthesis engine — VoiceBox is the optional alternative. Modelled on `doc-extract/` (self-contained, non-root uid 65532, `/health` endpoint) but see the base-image divergence below.

| File | Purpose |
|---|---|
| `piper-tts/main.py` | FastAPI app. `POST /piper/speak` — JSON `{"text": "..."}` → raw `audio/wav` (`Response(media_type="audio/wav")`). `_sanitize()` strips ASCII control chars (keeps `\t`/`\n`/`\r`); the route rejects empty/whitespace text (400) and text over `PIPER_MAX_TEXT_CHARS` (413). `_get_voice()` loads and caches the `PiperVoice` (kept out of import time so tests never need the model; wrapped in `_capped_session_options()` — see concurrency notes below); `_synthesize()` writes a WAV into an in-memory buffer via `wave` + `PiperVoice.synthesize_wav(...)`, wrapping any failure as `SynthesisError` → 500. `_lifespan` warms the model at startup when `PIPER_EAGER_LOAD` != `0`. No storage, no cache, no second endpoint — v1 is deliberately minimal |
| `piper-tts/Dockerfile` | Multi-stage **`python:3.12-slim`** build (digest-pinned), non-root uid 65532. Builder stage `ADD --checksum=sha256:…`s the voice model + config from `huggingface.co/rhasspy/piper-voices` @ `v1.0.0` (the checksum flag fails the build on any mismatch — the supply-chain equivalent of the Chainguard digest pins) then `chmod`s them world-readable; runtime stage copies packages + `voices/` + `main.py` |
| `piper-tts/requirements.txt` | Production dependencies (`fastapi`, `uvicorn`, `piper-tts`) |
| `piper-tts/requirements-test.txt` | Test dependencies (`pytest`, `httpx`, `flake8`, `black`) |
| `piper-tts/tests/test_main.py` | 17 pytest tests — `_sanitize`, `/health`, every `/piper/speak` branch (valid → 200 + `audio/wav`, empty/whitespace → 400, over-length → 413, missing field → 422, synthesis failure → 500), the route being a non-coroutine, `/health` staying responsive during a slow synth, and `_capped_session_options()` capping + restoring. **Synthesis is always mocked** (`_get_voice` / `_synthesize` via `monkeypatch`) and `conftest.py` sets `PIPER_EAGER_LOAD=0`, so CI never downloads the ~60 MB model |

**Base-image divergence (why not Chainguard):** `piper-tts` pulls in `onnxruntime`, whose manylinux wheel **segfaults (SIGSEGV) on `import onnxruntime`** under the `cgr.dev/chainguard/python:latest` distroless runtime — it links against `libstdc++`/`libgomp` that the distroless image does not ship, and there is no shell or package manager there to add them. The Chainguard `-dev` image imports it fine (confirming the missing runtime libs), and a full synth pipeline runs cleanly on `python:3.12-slim`. Per the global engineering standards' explicit allowance for `python:slim` + non-root, this one service uses `python:3.12-slim` — still multi-stage, digest-pinned, non-root uid 65532, read-only root FS. Every other service stays on Chainguard distroless.

**Voice model:** `en_US-lessac-medium` (`.onnx` ≈60 MB + `.onnx.json`). **Not committed to git** — fetched and SHA256-verified at image build time. Expected hashes are hard-coded in `piper-tts/Dockerfile`:
- `en_US-lessac-medium.onnx` → `sha256:5efe09e69902187827af646e1a6e9d269dee769f9877d17b16b1b46eeaaf019f`
- `en_US-lessac-medium.onnx.json` → `sha256:efe19c417bed055f2d69908248c6ba650fa135bc868b0e6abb3da181dab690a0`

To switch voices: change the `ADD` URLs + `--checksum` values in the Dockerfile and set `PIPER_VOICE` to the new basename (`docker-compose build piper-tts`).

**Config** (env vars, all optional — defaults baked in; documented in `.env.example`): `PIPER_VOICE` (default `en_US-lessac-medium`), `PIPER_LENGTH_SCALE` (speed, lower = faster, default `1.0`), `PIPER_MAX_TEXT_CHARS` (default `6000`), `PIPER_MODEL_DIR` (default `/app/voices`). Operational knobs, set in `piper-tts/Dockerfile` + `docker-compose.yml`, not usually touched: `PIPER_ORT_THREADS` / `OMP_NUM_THREADS` / `ORT_NUM_THREADS` etc. (all `1`), `PIPER_EAGER_LOAD` (`1`; `conftest.py` sets `0`).

**Concurrency / resource notes (PR #30 — a hang found in live compose verification):** the service works standalone but *wedged* under the compose CPU/PID limits until three things were fixed. (1) `POST /piper/speak` is a **sync `def`** route — ONNX inference is blocking CPU work, and in an `async` route it stalls the entire single-threaded event loop (so one slow synth kills `/health` and every other request); FastAPI runs sync routes in a worker threadpool. (2) onnxruntime is pinned to a **1-thread pool** via `_capped_session_options()` (a scoped monkeypatch of `onnxruntime.SessionOptions` around `PiperVoice.load()`, since piper exposes no thread config) *plus* `OMP_NUM_THREADS=1` & friends in the Dockerfile/compose — left unbounded it sizes the intra-op pool to the *host* core count, which under `cpus`/`pids` limits deadlocks during pool creation (the request never even reaches a log line). (3) `pids` was raised `30 → 128` and `memory` `512M → 768M` (measured peak RSS ≈ 220 MB). The model is loaded eagerly at startup so a broken model fails the healthcheck at boot, not mid-request. Live-verified in the running stack: `/piper/speak` returns a valid WAV in ~0.5 s, `/health` answers in 3 ms *during* a synth, concurrent requests don't wedge.

**Frontend:** `speakTextViaPiper(text, sourceBtn)` in `speech.js` `POST`s to `PIPER_SPEAK_URL` (`config.js`, default `https://localhost/piper/speak`), gets a `Blob`, plays it via the shared `ttsAudio` `<audio>` element through `_playTtsBlob()` — so Piper has a real stop control (`stopSpeaking()` pauses playback and `URL.revokeObjectURL`s the tracked blob URL). Recognition is paused for the duration (`_pauseRecognitionForSpeech()` / `_resumeRecognitionAfterSpeech()`) so the mic doesn't capture the audio. The pending fetch doubles as the "generating" spinner, exactly like the VoiceBox path.

## Nginx Proxy

The proxy in [deploy/nginx/nginx.conf](deploy/nginx/nginx.conf) uses **exact-match** or narrow prefix locations (`location = /ollama/api/chat`, `location = /ollama/api/tags`, `location = /piper/speak`, `location = /voicebox/speak`, `location ^~ /voicebox/audio/`, `location = /doc-extract/extract`, `location = /settings`, `location ^~ /settings/`) that accept only the HTTP methods each route needs — all other methods are denied at the nginx layer. The two `/settings` blocks allow `GET PUT POST` only, are on the `settings` zone (30 req/min, burst 10), and carry `auth_request_set $auth_user $upstream_http_x_auth_user;` + `proxy_set_header X-Auth-User $auth_user;` so the settings service receives the authenticated username (any client-supplied `X-Auth-User` is overwritten). Bodies are tiny JSON — default body cap and buffering. `/ollama/api/chat` (POST) and `/ollama/api/tags` (GET-only — reads the installed-model list for the toolbar model selector) are the **only** two Ollama paths reachable; every other Ollama path (`/api/generate`, `/api/pull`, `/api/delete`, `/api/create`, `/api/copy`, `/api/push`) is denied. The `ollama_chat` rate limit zone allows 5 requests/min with a burst of 5; `ollama_tags` allows 12 requests/min with a burst of 3 (default `client_max_body_size` and buffering — the response is small JSON, the request has no body — with a modest `proxy_read_timeout 30s`); `piper_speak` allows 10 requests/min with a burst of 3; `voicebox_speak` (shared by both VoiceBox locations) allows 10 requests/min with a burst of 3; `doc_extract` allows 10 requests/min with a burst of 3 (`limit_req_zone`). `proxy_buffering off` and `proxy_read_timeout 300s` on the Ollama location support streaming responses; `/piper/speak` sets `proxy_read_timeout 60s` (CPU synthesis of a few sentences takes at most a few seconds) plus `proxy_buffer_size 16k` + `proxy_buffers 128 16k` (2 MB) so a whole WAV is held in memory rather than spilled to a temp file — the tiny JSON request body needs no `client_max_body_size` bump; `/voicebox/speak` sets `proxy_read_timeout 90s` since it blocks on voicebox-proxy for the full synthesis duration (whose own httpx timeout is 60s); `/doc-extract/extract` raises `client_max_body_size` to `15m` to match doc-extract's own upload limit.

Security headers set on every response (all at the `server {}` level): `Strict-Transport-Security`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy`, `Referrer-Policy: no-referrer`, `Permissions-Policy`, and `Cache-Control: no-cache`. **`Cache-Control` must stay at the server level, never inside `location /`** — nginx drops *all* inherited `add_header` directives from a location the moment that location declares its own, so a `location /` `add_header` would silently strip the security headers from every static response. `no-cache` (not `no-store`) means the browser revalidates against nginx's ETag/Last-Modified: a cheap `304` for unchanged `src/aia/` assets, a fresh `200` the instant a file changes — so code changes are picked up on a normal reload with no `Ctrl+Shift+R`. The CSP is `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; media-src 'self' blob:; connect-src 'self'; form-action 'self'` — `script-src` has no inline/eval; `style-src 'unsafe-inline'` is for KaTeX only; `media-src … blob:` lets the page play the Piper TTS WAV it fetches from `/piper/speak` (see Security Invariants).

### `nginx.conf` is generated from a template

`deploy/nginx/nginx.conf` is **not hand-edited** — it is generated from `deploy/nginx/nginx.conf.template` by `deploy/nginx/render-nginx-conf.sh` (POSIX `sh` + `envsubst` with an explicit variable allowlist, so nginx's own `$host` / `$binary_remote_addr` / etc. are left untouched). The committed `nginx.conf` is the local-default render; the 9 deployment values below become `${...}` placeholders in the template:

| Env var | Default (reproduces the committed file) | Replaces |
|---|---|---|
| `AUTH_UPSTREAM` | `auth:9000` | `upstream auth_service` server |
| `VOICEBOX_PROXY_UPSTREAM` | `voicebox-proxy:8002` | `upstream voicebox_service` server |
| `DOC_EXTRACT_UPSTREAM` | `doc-extract:8003` | `upstream doc_extract_service` server |
| `PIPER_UPSTREAM` | `piper-tts:8004` | `upstream piper_service` server |
| `SETTINGS_UPSTREAM` | `settings-service:8005` | `upstream settings_service` server |
| `OLLAMA_UPSTREAM` | `host.docker.internal:11434` | `proxy_pass` host:port in `location = /ollama/api/chat` **and** `location = /ollama/api/tags` |
| `SERVER_NAME` | `localhost` | `server_name` in both `server {}` blocks |
| `SSL_CERT_PATH` | `/etc/nginx/ssl/localhost.pem` | `ssl_certificate` |
| `SSL_KEY_PATH` | `/etc/nginx/ssl/localhost-key.pem` | `ssl_certificate_key` |

**To change any of these, edit `nginx.conf.template`, then regenerate and commit both files:**

```bash
sh deploy/nginx/render-nginx-conf.sh > deploy/nginx/nginx.conf   # envsubst via `gettext`; or run it inside nginx:1.27-alpine
```

CI's `nginx-config-check` job enforces that the committed `nginx.conf` is exactly the default render (drift guard) and that a cloud-value render leaves no `${...}` placeholder unsubstituted, in addition to the existing `nginx -t`. `docker-compose` still mounts the committed `nginx.conf` (the local-default render) directly; full runtime/init-container templating for a non-local deployment is a deferred follow-up (see `docs/cloud-hardening-plan.md` Finding E).

If Ollama or Voicebox changes port, or the model changes, update `deploy/nginx/nginx.conf.template` (then regenerate) and/or `config.js` respectively, then restart the container.

Changes to `nginx.conf` are syntax-validated in CI via the `nginx-config-check` job (`nginx -t` inside `nginx:1.27-alpine`). To validate locally without Docker, reload the running container: `docker exec vpal-nginx /usr/sbin/nginx -s reload`.

Self-signed certs are in `deploy/certs/` (generated via mkcert). Nginx is configured for TLS 1.2+. Regenerate with mkcert targeting `localhost` if they expire.

## Updating Vendored Libraries

`marked.min.js`, `dompurify.min.js`, `katex.min.js`, `katex-auto-render.min.js`, `diff-match-patch.js`, and `css/katex.min.css` are all pinned with SHA-256 SRI hashes in `index.html`.

The docker-compose bind mount serves the working-copy bytes straight to the browser, so the served file must hash to exactly the `integrity=` value — a line-ending conversion between commit and checkout would be enough to break it. **All six assets are marked `binary` in `.gitattributes`**, so git applies no clean/smudge filter: the working copy, the committed blob, and every fresh checkout are byte-identical on any platform and under any `core.autocrlf` setting. Recompute the hash straight from the file and update the corresponding `integrity=` attribute:

```powershell
$bytes = [IO.File]::ReadAllBytes('src\aia\scripts\<filename>.js')   # or src\aia\css\<filename>.css
"sha256-" + [Convert]::ToBase64String([Security.Cryptography.SHA256]::Create().ComputeHash($bytes))
```

`npm run check:sri` (`scripts/check-sri.mjs`) re-hashes every `integrity=`-pinned file referenced from `index.html` and fails on any mismatch; CI runs it in the `frontend-lint` job on the clean Linux checkout, so a stale hash — or a re-vendored file whose `integrity=` wasn't updated — is caught before it can reach a browser. Run it locally after changing any vendored asset.

If you see a browser SRI error, run `npm run check:sri`; for each mismatch it prints the `integrity=` value from `index.html` alongside the freshly computed hash (and flags any CR bytes in the file) so you can see what disagrees.

KaTeX's font files (`src/aia/css/fonts/`) are referenced by `katex.min.css` via relative `url(fonts/...)` and are **not** individually SRI-pinned — SRI only covers the top-level `<script>`/`<link>` tag it's attached to, not resources that tag's content goes on to fetch. To re-vendor KaTeX from scratch (e.g. to bump its version): `npm pack katex@<version>` in a scratch directory, then copy `dist/katex.min.js` → `scripts/katex.min.js`, `dist/contrib/auto-render.min.js` → `scripts/katex-auto-render.min.js`, `dist/katex.min.css` → `css/katex.min.css`, and the entire `dist/fonts/` directory → `css/fonts/`.

**Inter** (`src/aia/css/fonts/inter-latin-wght-{normal,italic}.woff2`) — the UI body font, `@font-face`-declared at the top of `style.css`. Not SRI-pinned (same reason as KaTeX's fonts). To re-vendor / bump: `npm pack @fontsource-variable/inter` in a scratch dir, `tar xzf` it, copy **only** `package/files/inter-latin-wght-normal.woff2` + `inter-latin-wght-italic.woff2` (the latin-subset variable files, ~100 KB total — skip the other language subsets and the `opsz`/`standard` axes) into `src/aia/css/fonts/`. `*.woff2 binary` in `.gitattributes` keeps git from touching them.

**diff-match-patch** — source: <https://github.com/google/diff-match-patch>, file `javascript/diff_match_patch_uncompressed.js` (the official *uncompressed* build). Vendored **verbatim** as `src/aia/scripts/diff-match-patch.js` (do not edit it — it is ESLint-ignored via `eslint.config.js`, not renamed to `*.min.js`). It ships no `module.exports` block, but its trailing `this['diff_match_patch'] = …` / `this['DIFF_*'] = …` lines resolve to `window` in a classic browser script *and* to `module.exports` under Node/Jest (`this === module.exports` in a CommonJS module), so it serves as both the browser global and the Jest import with no modification. To re-vendor: `curl -sSL -o src/aia/scripts/diff-match-patch.js https://raw.githubusercontent.com/google/diff-match-patch/master/javascript/diff_match_patch_uncompressed.js`, recompute the SRI hash with the snippet above, update `index.html`.

**highlight.js** — currently **v11.11.1**, "common" languages build (~40 languages). Script source: <https://cdnjs.cloudflare.com/ajax/libs/highlight.js/11.11.1/highlight.min.js> (identical to `@highlightjs/cdn-assets`'s `highlight.min.js`). Dark theme: <https://cdnjs.cloudflare.com/ajax/libs/highlight.js/11.11.1/styles/atom-one-dark.min.css> → `src/aia/css/highlight.min.css` (vendored verbatim; the `#282c34` → `#1e293b` background match is done in `style.css`, not by editing this file). Both are `binary` in `.gitattributes` and SRI-pinned. To bump: download both files at the new version, recompute both SRI hashes with the snippet above, update `index.html`.

**Mermaid** — currently **v10.9.3**. Source: the `mermaid` npm package's `dist/mermaid.min.js` (UMD single-file bundle) — `npm pack mermaid@10.9.3` in a scratch dir, then `tar -xzf mermaid-10.9.3.tgz package/dist/mermaid.min.js` and copy to `src/aia/scripts/mermaid.min.js`. **Stay on the 10.9.x line** — Mermaid v11 restructured away from a clean UMD build. `binary` in `.gitattributes`, SRI-pinned. To bump within 10.9.x: re-pack, recompute the SRI hash, update `index.html`; then re-run the CSP gate (see [Diagrams (Mermaid)](#diagrams-mermaid)) — a browser check for `script-src`/`unsafe-eval` violations, not just `nginx -t`.

Paste the output into the matching `integrity="..."` attribute in `index.html`. The browser will refuse to load the script if the hash does not match.
